## 2. Star schema memakai dim_tanggal standar, dim_produk mengikuti struktur standar
Penjelasan Star Schema :

Berdasarkan diagram star schema pada proses bisnis pembelian (fact_purchasing), tabel dim_date dan dim_product telah dirancang sesuai dengan standar data warehouse berdasarkan metodologi Kimball. Tabel dim_date memiliki atribut waktu yang lengkap, mulai dari hari, bulan, kuartal, dan tahun hingga penanda akhir pekan (is_weekend) serta tahun fiskal. Dimensi ini juga menerapkan konsep role-playing dimension dengan menghubungkan tiga kunci waktu pada tabel fact_purchasing, yaitu order_date_key, due_date_key, dan ship_date_key, sehingga analisis dapat dilakukan berdasarkan tahapan transaksi pembelian. Sementara itu, tabel dim_product mencakup informasi identitas produk, spesifikasi fisik, harga, stok minimum, serta hierarki kategori dan subkategori yang telah didenormalisasi. Selain itu, atribut start_date, end_date, dan is_current_flag menunjukkan bahwa dimensi produk telah mendukung penerapan metode Slowly Changing Dimension (SCD) untuk mencatat dan memantau perubahan informasi produk dari waktu ke waktu.

## 5. Tabel Fakta: FactSales
* **Target Table:** `FactSales`
* **Source Table(s):** `Sales.SalesOrderHeader`, `Sales.SalesOrderDetail`, `DimCustomer`, `DimProduct`, `DimTerritory`, `dim_tanggal`

| Target Column | Target Data Type | Primary / Foreign Key | Source Table(s) | Source Column / Logic Transformation | Transformation / Business Rules |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `SalesFactID` | BIGINT (AUTO_INCREMENT) | Primary Key | N/A | Generated by ETL | Primary Key unik tabel fakta. |
| `SalesOrderID` | INT | Degenerate Dimension | `Sales.SalesOrderHeader` | `SalesOrderID` | Nomor transaksi header dari OLTP. |
| `SalesOrderDetailID` | INT | Degenerate Dimension | `Sales.SalesOrderDetail` | `SalesOrderDetailID` | Detail rincian baris transaksi. |
| `CustomerSK` | INT | Foreign Key | `DimCustomer` | Lookup to `DimCustomer.CustomerSK` via `SalesOrderHeader.CustomerID = DimCustomer.CustomerID` | Surrogate key dari tabel dimensi pelanggan. |
| `ProductSK` | INT | Foreign Key | `DimProduct` | Lookup to `DimProduct.ProductSK` via `SalesOrderDetail.ProductID = DimProduct.ProductID` | Surrogate key dari tabel dimensi produk. |
| `TerritorySK` | INT | Foreign Key | `DimTerritory` | Lookup to `DimTerritory.TerritorySK` via `SalesOrderHeader.TerritoryID = DimTerritory.TerritoryID` | Surrogate key dari tabel dimensi wilayah. |
| `tanggal_key` | INT | Foreign Key | `dim_tanggal` | Lookup to `dim_tanggal.tanggal_key` via `COALESCE(DATE_FORMAT(SalesOrderHeader.OrderDate, '%Y%m%d'), -1)` | Merujuk ke `dim_tanggal.tanggal_key`. Gunakan `-1` jika tanggal kosong/NULL. |
| `OrderQty` | INT | Metric / Measure | `Sales.SalesOrderDetail` | `OrderQty` | Jumlah kuantitas barang yang dibeli. |
| `UnitPrice` | DECIMAL(18,2) | Metric / Measure | `Sales.SalesOrderDetail` | `UnitPrice` | Harga satuan barang. |
| `UnitPriceDiscount` | DECIMAL(18,2) | Metric / Measure | `Sales.SalesOrderDetail` | `UnitPriceDiscount` | Nilai diskon satuan. |
| `LineTotal` | DECIMAL(18,2) | Metric / Measure | `Sales.SalesOrderDetail` | `LineTotal` | Calculated: `(OrderQty * UnitPrice) * (1 - UnitPriceDiscount)`. |
| `TaxAmt` | DECIMAL(18,2) | Metric / Measure | `Sales.SalesOrderHeader` | `TaxAmt * (LineTotal / SubTotal)` | Biaya pajak dihitung proporsional per baris detail. |
| `Freight` | DECIMAL(18,2) | Metric / Measure | `Sales.SalesOrderHeader` | `Freight * (LineTotal / SubTotal)` | Biaya pengiriman dihitung proporsional per baris detail. |

## Urutan Load ETL (Load Order)

1. **Memuat Seluruh Tabel Dimensi Terlebih Dahulu (Parallel / Independent Load)**
   Sebelum tabel fakta dapat diisi, semua tabel dimensi harus sudah terisi terlebih dahulu agar nilai *Surrogate Key* (SK) dapat dicari (*lookup*). Urutan pengisian tabel dimensi bisa dilakukan secara bersamaan (paralel) karena tidak saling bergantung satu sama lain:
   - `dim_tanggal` (Dapat di-*generate* langsung menggunakan CTE rekursif tanpa bergantung pada tabel OLTP).
   - `DimCustomer` (Mengambil data dari `Sales.Customer`, `Person.Person`, dll).
   - `DimProduct` (Mengambil data dari `Production.Product`, `ProductSubcategory`, dan `ProductCategory`).
   - `DimTerritory` (Mengambil data dari `Sales.SalesTerritory` dan `Person.CountryRegion`).

2. **Memuat Tabel Fakta (`FactSales`)**
   - `FactSales` (Dilakukan paling akhir setelah seluruh tabel dimensi di Langkah 1 selesai terisi).
   - **Alasan:** Tabel fakta membutuhkan proses *lookup* ke kolom `CustomerSK`, `ProductSK`, `TerritorySK`, dan `tanggal_key` yang bersumber dari tabel-tabel dimensi di atas.


## 4. Strategi SCD tertulis

# Strategi Slowly Changing Dimension (SCD) - Skema Purchasing

Dokumen ini memuat penentuan strategi SCD untuk tiap tabel dimensi pada skema *Purchasing*, beserta tipe yang digunakan untuk kolom-kolom penting dan alasannya.

## 1. `dim_product` (Kombinasi SCD Type 1 & Type 2)
*   **SCD Type 2 (History Retained):** `standard_cost`, `list_price`, `subcategory_name`.
    *   *Alasan:* Ini adalah dimensi paling krusial untuk memakai Type 2. Perubahan harga (`standard_cost` dan `list_price`) wajib dilacak historinya. Jika vendor menaikkan harga material tahun ini, kita tidak boleh menimpa data harga tahun lalu agar perhitungan `line_total` dan metrik pengeluaran masa lalu tidak berubah dan tetap akurat.
*   **SCD Type 1 (Overwrite):** `product_name`, `color`, `size`, `weight`.
    *   *Alasan:* Jika ada koreksi ejaan nama barang atau pembaruan spesifikasi fisik, cukup timpa data lama. Hal ini tidak merusak metrik finansial riwayat pesanan.

## 2. `dim_vendor` (Kombinasi SCD Type 1 & Type 2)
*   **SCD Type 2:** `credit_rating`, `preferred_vendor_status`.
    *   *Alasan:* Status vendor memengaruhi keputusan bisnis. Jika sebuah vendor turun *credit rating*-nya atau dicabut status "preferred"-nya, kita butuh historinya untuk menganalisis apakah penurunan status ini berkorelasi dengan tingginya jumlah barang yang direjeksi (`rejected_qty`) pada periode waktu tersebut.
*   **SCD Type 1:** `vendor_name`, `account_number`, `purchasing_web_service_url`.
    *   *Alasan:* Pembaruan URL sistem vendor atau perubahan nama legal perusahaan murni bersifat perbaikan administratif.

## 3. `dim_employee` (Kombinasi SCD Type 1 & Type 2)
*   **SCD Type 2:** `job_title`.
    *   *Alasan:* Jika staf *purchasing* mendapat promosi jabatan, riwayat kinerjanya saat ia masih berada di posisi bawah harus dikaitkan dengan jabatannya saat itu, bukan ditimpa dengan jabatan barunya.
*   **SCD Type 1:** `employee_name`, `marital_status`, `vacation_hours`, `sick_leave_hours`.
    *   *Alasan:* Perubahan status pernikahan atau jatah sisa cuti adalah data SDM operasional yang tidak relevan dengan histori analisis performa pembelian. Selalu gunakan data paling mutakhir.

## 4. `dim_ship_method` (SCD Type 2)
*   **SCD Type 2:** `ship_base`, `ship_rate`.
    *   *Alasan:* Tarif dasar logistik dari perusahaan ekspedisi pasti berfluktuasi dari tahun ke tahun. Jika tarif baru menimpa tarif lama (Type 1), kalkulasi perbandingan biaya pengiriman historis akan rusak. Harus dibuat baris baru (Type 2) tiap ada perubahan tarif.

## 5. `dim_geography` (SCD Type 1)
*   **SCD Type 1:** `city`, `state_province_name`, `postal_code`.
    *   *Alasan:* Entitas wilayah sangat jarang berubah. Jika ada pemekaran provinsi atau pembetulan kode pos, dampaknya terhadap histori pengadaan barang sangat minim sehingga cukup di-*overwrite*.

## 6. `dim_date` (SCD Type 0)
*   **SCD Type 0 (Retain Original):** Semua atribut tanggal.
    *   *Alasan:* Tanggal bersifat statis. Atribut sebuah hari (misalnya tanggal 5 November 2026 adalah hari Kamis) selamanya akan sama. Tidak akan pernah ada perubahan data yang perlu dilacak.

---
**Catatan Implementasi:**
Karena `dim_product`, `dim_vendor`, `dim_employee`, dan `dim_ship_method` menerapkan **SCD Type 2**, maka desain tabel fisik untuk keempat tabel tersebut harus ditambahkan kolom *tracking* standar, yaitu:
1. `start_date` (Kapan versi data ini mulai berlaku)
2. `end_date` (Kapan versi data ini berakhir/kedaluwarsa)
3. `is_current_flag` (Penanda apakah ini baris data yang paling aktif saat ini)
